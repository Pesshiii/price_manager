# PRD: Dataframe Preview — производительность и диагностика ошибок pipeline

## Problem Statement

При работе с pipeline-редактором в dataframe-приложении пользователь сталкивается с двумя проблемами:

1. **Медленное превью для больших файлов.** Загрузка XLSX 5–30 MB (30k–200k строк) превращает DataFrame в 50–500 MB в памяти (строковые объекты Python). Существующий reader-кэш использует `pickle` и имеет ограничение 50 MB — такие файлы никогда не кэшируются. Каждый preview-запрос повторно парсит XLSX с нуля (1–5 секунд задержки), делая интерактивную сборку pipeline невыносимой.

2. **Невозможность диагностировать ошибки в шагах.** Когда один из трансформов падает с исключением, preview-эндпоинт возвращает только объект ошибки без данных, а `step_index` в ответе указывает на запрошенный предел (`up_to`), а не на реально сломанный шаг. Пользователь видит пустой экран и не знает, на каком шаге произошла ошибка, и как выглядели данные до неё.

## Solution

1. **Заменить pickle на Apache Arrow/Feather** для reader-кэша. Feather с zstd-сжатием даёт 5–10× компрессию относительно pickle, укладывая типичные XLSX-каталоги под новый предел 200 MB. После первого preview файл мгновенно загружается из Redis на все последующие запросы.

2. **Изменить семантику `apply_partial`** так, чтобы шаги выполнялись по одному с перехватом исключений. При ошибке в шаге K pipeline останавливается и возвращает DataFrame в состоянии после шага K−1 вместе с описателем ошибки `step_error`. Preview-эндпоинт всегда отвечает HTTP 200 с данными + опциональным `step_error`.

## User Stories

1. Как редактор pipeline, я хочу, чтобы превью появлялось мгновенно при повторных запросах, чтобы я мог итерировать конфигурацию шагов без ожидания.
2. Как редактор pipeline, я хочу видеть таблицу данных после первого успешного шага, даже если последующий шаг содержит ошибку, чтобы понять, как выглядят данные до проблемного места.
3. Как редактор pipeline, я хочу видеть точный индекс (0-based) сломанного шага и текст исключения, чтобы сразу перейти к нужному шагу и исправить конфиг.
4. Как редактор pipeline, я хочу, чтобы корректные шаги до ошибочного не перезапускались заново из-за наличия ошибки в последующем шаге.
5. Как разработчик, я хочу, чтобы при отсутствии ошибок `step_error` был `null`, чтобы SPA мог использовать единый тип ответа для обоих случаев.
6. Как разработчик, я хочу, чтобы Celery-задача импорта (`apply_pipeline`) по-прежнему бросала исключение при сломанном шаге, а не возвращала ошибку молча.
7. Как администратор, я хочу, чтобы первый preview после деплоя был единственным медленным запросом (cold cache miss), а не каждый.
8. Как разработчик, я хочу, чтобы reader-кэш работал на LocMemCache в тестах и на django-redis в проде без изменения кода кэширования.
9. Как редактор pipeline, я хочу загружать CSV любого размера и получать мгновенный отклик для повторных preview-запросов.
10. Как редактор pipeline, я хочу, чтобы при ошибке reader-стадии (неверный формат файла, устаревшая сессия) я получал HTTP 404/500, а не пустую таблицу с `step_error`.

## Implementation Decisions

### Модуль 1: Reader-кэш (`dataframe/cache.py`)

- Сериализация меняется с `pickle` на `pyarrow.feather` (`df.to_feather(buf, compression='zstd')`).
- Десериализация: `pd.read_feather(io.BytesIO(raw))`.
- Константа `MAX_PICKLE_BYTES` переименовывается в `MAX_CACHE_BYTES` и поднимается до 200 MB. Размер проверяется по сжатому (`len(blob)`), а не по in-memory `memory_usage`.
- Интерфейс функций (`get_cached_reader_df`, `set_cached_reader_df`) не меняется — обратная совместимость с вызывающим кодом сохраняется.
- `pyarrow` уже присутствует в `requirements.txt` — новая зависимость не добавляется.
- Старые pickle-ключи в Redis будут cache miss при деплое (одноразовое замедление).
- На LocMemCache (`bytes`-совместимый бэкенд) Feather-блоб хранится как `bytes` — поведение не меняется.

### Модуль 2: Pipeline executor (`dataframe/services.py`)

- Сигнатура `apply_partial` меняется: возвращает `tuple[pd.DataFrame, dict | None]`.
  - При успехе: `(df, None)`
  - При ошибке шага K: `(df_до_K, {"step_index": K, "message": "<ExcType>: <message>"})`
  - Ошибка reader-стадии по-прежнему бросается — не оборачивается в tuple.
- Внутри цикла по трансформам: каждый шаг оборачивается в `try/except Exception`. При исключении возвращаем текущий `df` (не мутированный, т.к. все трансформы создают копию) и `step_error`.
- Функция `apply` распаковывает `(df, err)` и при `err is not None` бросает `RuntimeError(err["message"])` — внешний контракт для Celery-задач не меняется.

### Модуль 3: Preview API (`dataframe/api/views.py`)

- `PreviewView.post` убирает `try/except` вокруг `apply_partial`.
- Распаковывает `(df, step_error)`.
- Вспомогательная функция `_dataframe_to_payload` принимает опциональный `step_error` и включает его в ответ.
- Итоговый контракт ответа:
  ```
  {
    "columns": [...],
    "rows": [...],
    "total_rows": int,
    "returned_rows": int,
    "offset": int,
    "has_more": bool,
    "step_error": {"step_index": int, "message": str} | null
  }
  ```
- HTTP 200 всегда при успешном выполнении reader-стадии.
- HTTP 404 — сессия не найдена; HTTP 500 — ошибка reader.

## Testing Decisions

**Что считается хорошим тестом:** тест проверяет внешнее поведение (контракт функции/эндпоинта), а не внутреннюю реализацию. Нельзя проверять, что используется `pyarrow` — нужно проверять, что второй вызов возвращает тот же DataFrame. Нельзя проверять структуру ошибки внутри `apply_partial` — нужно проверять поведение через `PreviewView`.

**Модули с тестами:**

### `dataframe/cache.py` — unit
- Feather round-trip: сохранить DataFrame → получить идентичный.
- DataFrame > 200 MB: кэш не пишется, функция возвращает `False`.
- Backend fail (mock `cache.set` бросает): функция возвращает `False`, не бросает.
- Backend fail (mock `cache.get` бросает): возвращает `None`.
- Существующий тест `test_apply_partial_stops_early` в `dataframe/tests.py` — обновить распаковку tuple.

### `dataframe/services.py` — unit
- Успешный pipeline: `(df, None)`.
- Ошибка в шаге 0: `(df_reader_output, {step_index: 0, ...})`.
- Ошибка в шаге 2 из 4: `(df_после_шага_1, {step_index: 2, ...})`.
- `apply()` при ошибке шага бросает исключение (не возвращает tuple).
- Приор: `PipelineTests` в `dataframe/tests.py`.

### `dataframe/api/views.py` — integration (APIClient)
- Успешный preview: ответ содержит `step_error: null`, HTTP 200.
- Preview с ошибочным шагом: ответ содержит данные ненулевой длины + `step_error.step_index`.
- Несуществующая сессия: HTTP 404.
- Приор: `dataframe/test_api.py`.

## Out of Scope

- Пошаговый кэш трансформов (кэш после каждого шага). Трансформы выполняются в памяти < 500ms — reader-кэш решает основную проблему.
- Eager Parquet-конвертация при upload. Фиксирует reader-конфиг в момент загрузки; нельзя менять лист/заголовок интерактивно.
- Режим «продолжить после ошибки» (skip-and-collect-all-errors). Ошибка в шаге 2 может скрыть ошибку в шаге 4; stop-at-first — более безопасная семантика.
- Изменения в SPA (`price-manager-frontend`) — описан только серверный контракт.
- Инвалидация старых pickle-ключей в Redis при деплое. Это операционная задача (они expire по TTL 1h).

## Further Notes

- Все текущие трансформы начинают с `df.copy()` — при исключении входной `df` не мутируется. Это свойство необходимо для корректного возврата состояния до ошибочного шага; при добавлении новых трансформов это соглашение должно соблюдаться.
- Первый preview-запрос после деплоя всегда будет медленным (cold cache miss из-за смены формата). Это ожидаемо и происходит один раз на сессию.
