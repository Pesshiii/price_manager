# ADR-0002: Arrow/Feather вместо pickle для reader-кэша DataFrame

**Статус:** Принято — 2026-05-25

## Контекст

Reader-стадия pipeline (парсинг XLSX/CSV) кэшируется в Redis. До этого решения
кэш использовал `pickle.dumps(df)` + ограничение 50 MB на сериализованный объект.

Проблема: `df.memory_usage(deep=True).sum()` для DataFrame с текстовыми столбцами
даёт 10–50× больше размера файла на диске. Типичный XLSX 5–30 MB создаёт DataFrame
50–500 MB; такие файлы никогда не попадали в кэш, и каждый preview-запрос
перечитывал и парсил файл заново (1–5 сек).

## Решение

Сериализация через `pyarrow.feather` (`df.to_feather(buf, compression='zstd')`).
Предел `MAX_CACHE_BYTES` поднят до 200 MB (проверяется по сжатому размеру).

## Рассмотренные альтернативы

| Альтернатива | Почему отклонена |
|---|---|
| `zlib.compress(pickle(df))` | 3–5× сжатие против 5–10× у Feather; медленнее десериализация |
| Eager Parquet на upload | Фиксирует reader-конфиг в момент загрузки; нельзя менять лист/заголовок интерактивно |
| Поднять лимит pickle без сжатия | Redis хранит сырые гигабайты; при многих сессиях заканчивается память |

## Последствия

- `pyarrow` уже в `requirements.txt` — нет новых зависимостей.
- Функции `get_cached_reader_df` / `set_cached_reader_df` в `dataframe/cache.py`
  используют `io.BytesIO`; совместимость с LocMemCache (тесты) сохраняется.
- Старые pickle-блобы в Redis несовместимы с Feather — при деплое все reader-кэши
  окажутся cache miss, первый preview после деплоя будет медленным (один раз).
