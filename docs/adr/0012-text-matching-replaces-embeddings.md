# ADR-0012: Текстовый матчинг (pg_trgm + rapidfuzz) вместо эмбеддингов в SupplierFeed

**Статус:** Принято

## Контекст

Матчинг строк выгрузки с `Product` реализовывался через косинусное сравнение эмбеддингов (`nomic-embed-text` через Ollama). На текущем этапе каталог наполняется почти исключительно из выгрузок поставщиков, и скорость матчинга критична. HTTP-вызов к внешнему embedder-сервису на каждую незакэшированную строку создаёт неприемлемую задержку при обработке больших выгрузок.

Дополнительно: названия товаров у поставщиков практически идентичны названиям в каталоге с незначительными вариациями (пропущенный пробел, другой порядок слов). Семантический поиск избыточен для такого уровня схожести.

## Решение

Заменить эмбеддинг-матчинг (шаг 3 алгоритма) на двухэтапный текстовый матчинг:

1. **DB pre-filter**: `pg_trgm similarity(Product.name, entry_name) > low_match_threshold` по GIN-индексу — возвращает top-10 кандидатов без внешних сервисов.
2. **Python re-rank**: `rapidfuzz.token_sort_ratio` по каждому из 10 кандидатов — нечувствителен к порядку слов, итог top-5.

Ввести два порога в `FeedMapping` (вместо одного `auto_match_threshold`):
- `auto_match_threshold` (по умолчанию 0.92) — выше → авто-матч
- `low_match_threshold` (по умолчанию 0.50) — ниже → MatchQueue без кандидатов

`FeedMapping.identity_columns` удалить; `product_name_column` переименовать в `name_column` и сделать обязательным (используется и для матчинга, и для создания товара).

Полностью удалить инфраструктуру эмбеддингов: `Product.embedding`, `embedding_text_hash`, `embed_products_task`, `post_save`-сигнал, beat-задачу `embed_missing_products`, management-команду `embed_products`, `product/services/embeddings.py`, контейнер `embedder` из docker-compose. Гибридный поиск (`/api/products/products/?q=`) переходит на чисто лексический режим.

## Рассмотренные альтернативы

- **Оставить эмбеддинги**: неприемлемая скорость обработки на текущем этапе наполнения каталога.
- **Только pg_trgm без Python re-rank**: `similarity()` чувствительна к порядку слов — `"Дрель Bosch 500W"` vs `"Bosch 500W Дрель"` дают заниженный скор; `token_sort_ratio` решает это без накладных расходов.

## Следствия

- Матчинг не требует внешних сервисов — скорость ограничена только БД и CPU.
- `pg_trgm` расширение должно быть включено (стандартное расширение PostgreSQL, не требует сторонних зависимостей).
- `rapidfuzz` добавляется в `requirements.txt`.
- Гибридный поиск по каталогу теряется до тех пор, пока эмбеддинги не будут возвращены целенаправленно (отдельное решение).
- При возврате к эмбеддингам в будущем — отдельный ADR; текущий алгоритм подменяется в `matcher.py` без изменения интерфейса `MatchQueue`.
