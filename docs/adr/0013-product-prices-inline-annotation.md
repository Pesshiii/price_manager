# ADR-0013: Цены продуктов возвращаются inline в product list через аннотацию

**Статус:** Принято

## Контекст

На странице каталога товаров пользователь может включить ценовые колонки (по одной на `PriceType`). Данные о ценах хранятся в `ProductPrice` (`pricing` приложение) — отдельной таблице, ключ `(product, supplier, price_type)`. Продуктовый list-эндпоинт (`GET /api/products/products/`) об этой таблице не знает.

Нужно было выбрать способ получения цен для отображения.

## Решение

Расширить `GET /api/products/products/` параметром `?price_types=<slug>,<slug>`. При его наличии бэкенд аннотирует каждый продукт в выдаче минимальной ценой по каждому запрошенному типу среди всех поставщиков. Форма ответа: поле `prices: { [slug]: number | null }` добавляется к каждому продукту в `results`.

Фильтрация по цене реализуется параметрами `?price_type=<slug>&price_min=<N>&price_max=<N>` через `EXISTS`-подзапрос на `ProductPrice` — без join-а в основной QuerySet.

## Рассмотренные альтернативы

- **Отдельный запрос** — после получения списка продуктов SPA делает второй запрос `GET /api/pricing/prices/?product__in=1,2,...`. Проблемы: N+1 при смене страницы, race condition между пагинацией и ценами (пока грузятся цены, продукты уже другие), дополнительная логика склейки на фронте.

## Следствия

- `GET /api/products/products/` пересекает границу приложений `product` и `pricing`. Это осознанное нарушение: цены — неотъемлемая часть каталожного представления товара.
- Поле `prices` присутствует в ответе только при явном запросе `?price_types=...`; без него форма ответа не меняется — обратная совместимость сохраняется.
- Аннотация использует `MIN(value)` по поставщикам — если нужны цены конкретного поставщика, это отдельный сценарий, не покрытый текущим решением.
- `API_MAP.md` должен отражать новый параметр `price_types` и поле `prices` в ответе.
