# ADR-0007: MatchQueue — сортировка по скору и bulk-создание товаров

**Статус:** Принято  
**Дата:** 2026-06-01

## Контекст

MatchQueue содержит неоднородные записи: одни имеют высокий скор сходства (почти авто-матч), другие — низкий (явно новый товар), третьи — вообще без кандидатов (аномалия, эмбеддер был недоступен). При сортировке по `id` пользователь не видит этой разницы и вынужден разбирать записи в случайном порядке.

Требование: ускорить разбор очереди. Пользователь хочет сначала разобрать вероятные совпадения вручную, а затем одним действием создать новые товары для хвоста с низкими скорами.

## Решения

### 1. Денормализация `best_score` в отдельную колонку

`SupplierFeedEntry` получает поле `best_score: FloatField(null=True)`. Матчер заполняет его при создании записи: `best_score = candidates[0].score` если есть кандидаты, `NULL` если кандидатов нет.

**Альтернатива:** извлекать скор из JSON на лету: `RawSQL("(match_candidates->0->>'score')::float", [])`. Не требует миграции, но без индекса — полный скан JSON-поля на каждый запрос очереди.

**Почему выбрана денормализация:** согласуется с ADR-0005 (кандидаты уже денормализованы в момент матчинга). `best_score` — атрибут той же операции. Очередь может содержать тысячи записей; колонка индексируется, запрос остаётся O(log n).

### 2. Порядок сортировки: `ORDER BY best_score DESC NULLS FIRST`

Записи с `best_score = NULL` (нет кандидатов) идут **первыми** — как аномалия, требующая внимания: эмбеддер мог быть недоступен при матчинге, и неизвестно, есть ли аналог в БД. Затем идут записи с убыванием скора.

**Альтернатива:** `NULLS LAST` — трактовать пустые кандидаты как «точно новый товар» (скор = 0). Отклонено: пустые кандидаты — это неопределённость, а не уверенность в отсутствии аналога.

### 3. Bulk-создание: один запрос для всей оставшейся очереди

Новый эндпоинт `POST .../queue/bulk-create-products/` с телом `{name_column: str}`. Создаёт `Product(draft)` + `SupplierLink` для всех `product=None, skipped=False` записей сессии.

**Альтернативы рассматривались:**
- *Быстрый режим «следующий»* (пер-энтри, ускоренный UI) — снижает трение, но не даёт выигрыша в скорости для большого хвоста.
- *Мульти-выбор + bulk action* — гибче, но сложнее в реализации и UX.

Выбран bulk всей очереди: пользователь сам определяет момент переключения — разобрав высокоскоровые записи вручную, жмёт кнопку для остатка.

### 4. Выбор колонки `name`: всегда диалог подтверждения

Диалог показывается **всегда**, даже если `FeedMapping.product_name_column` настроен. Предзаполнен этим значением, но пользователь может изменить.

**Альтернатива:** адаптивно — если `product_name_column` задан, пропускать диалог. Отклонено: настройка в `FeedMapping` могла устареть; явное подтверждение страхует от массового создания товаров с неверным именем.

### 5. SKU в bulk-создании

Берётся из `entry.data[FeedMapping.product_sku_column]` если колонка настроена, иначе из `entry.supplier_sku`. Переиспользует семантику уже существующего поля `FeedMapping.product_sku_column`.

### 6. Поведение при ошибках: skip-and-continue

Записи с конфликтом SKU или отсутствующей колонкой `name` пропускаются и остаются в очереди без изменений. Ответ: `{created: int, failed: int, errors: [{entry_id, reason}]}`. Пользователь видит сводку и разбирает проблемные вручную.

**Альтернатива:** abort-on-first-error — откат всей транзакции. Отклонено: теряет успешно созданные записи; для большого хвоста неприемлемо.

## Последствия

- Миграция: добавить `best_score` в `SupplierFeedEntry`.
- Матчер (`matcher.py`): заполнять `best_score` при создании каждой записи.
- API: новый эндпоинт `bulk-create-products`; `queue` endpoint меняет сортировку.
- Сериализатор `SupplierFeedEntrySerializer`: добавить `best_score` в `fields`.
