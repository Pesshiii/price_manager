# ADR-0005: match_candidates денормализуется в момент матчинга

## Статус

Принято

## Контекст

Фронтенд очереди матчинга (`MatchQueue`) должен показывать пользователю достаточно информации о каждом кандидате-товаре, чтобы можно было принять решение о подвязке: имя, артикул каталога (`sku`), категория и бренд.

`SupplierFeedEntry.match_candidates` — JSONB-поле, которое записывается один раз в `matcher.py` и хранится без изменений. Было два пути обогатить кандидатов нужными полями:

**А. Денормализовать при матчинге** — записать `sku`, `category`, `brand` прямо в JSONB в момент создания записи.

**Б. Обогащать при чтении** — хранить только `product_id`/`score`/`name`, а при отдаче очереди делать `Product.objects.filter(pk__in=все_candidate_ids)` и подмешивать данные в сериализаторе.

## Решение

Выбран вариант **А** — денормализация в момент матчинга.

`match_candidates` хранит объекты формата:

```json
{"product_id": 42, "score": 0.87, "name": "Насос центробежный", "sku": "NB-100", "category": "Насосы", "brand": "Grundfos"}
```

`SupplierFeedEntry.data` хранит объединение identity-колонок и переменных колонок (`{**identity_data, **variable_data}`), чтобы фронтенд видел полный контекст строки поставщика.

## Причины

- Очередь матчинга живёт часы/дни — риск устаревания category/brand за это время пренебрежимо мал.
- Вариант Б требует bulk-join в сериализаторе (до 100 product-записей на страницу из 20 записей × 5 кандидатов), усложняет код без реальной выгоды.
- Данные на момент матчинга — именно тот контекст, который релевантен для принятия решения.

## Последствия

- Записи, созданные до этого ADR, не содержат `sku`/`category`/`brand` в кандидатах. Фронтенд обрабатывает отсутствующие поля как `null` — data-миграция не проводится.
- `matcher.py` делает `select_related('category', 'brand')` при построении candidate-запроса.
