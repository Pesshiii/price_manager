# Глоссарий предметной области — Price Manager

## Импорт (ImportJob)

**Импорт** — разовая операция загрузки файла поставщика для обновления **постоянных** характеристик товара (`Product.characteristics`, `sku`, `name`, `category` и т.д.). Выполняется через `ImportJob` (preview → commit). Не путать с Выгрузкой.

**rows_total** — общее число строк в DataFrame после применения pipeline. Устанавливается один раз, до начала записи в БД. Включает невалидные строки.

**rows_done** — число строк, *обработанных* воркером (валидных + пропущенных). Растёт после каждого батча. Не равно числу успешно записанных строк — итоговую разбивку (created / updated / skipped) см. в `ImportJob.result`.

**Прогресс-батч** — порция строк размером `IMPORT_COMMIT_BATCH_SIZE`, каждая в отдельной транзакции. После записи батча `rows_done` обновляется через `progress_callback`.

**Indeterminate-фаза** — стадии до начала записи в БД (`STAGE_OPENING_SESSION`, `STAGE_APPLYING_PIPELINE`, `STAGE_VALIDATING_ROWS`). В это время `rows_total == 0`; клиент показывает spinner. Отдельного флага `is_determinate` нет — `rows_total > 0` является достаточным условием для перехода на progress bar.

**Прогресс при ошибке** — если задача падает посередине коммита, `rows_done` не сбрасывается. Значение отражает реально обработанные строки (каждый батч — своя транзакция, откат не происходит). SPA показывает застывший bar с иконкой ошибки.

**Прогресс CharacteristicMutationJob** — `retype` и `rename` используют тот же паттерн: `rows_total` устанавливается через `COUNT` до начала итерации; `rows_done` — число пройденных продуктов (включая `skip_row` в rename). `rows_done` обновляется каждые `batch_size` итераций независимо от того, попал ли продукт в батч: скипнутые строки не пишутся в БД, но всё равно двигают счётчик. SPA может использовать тот же progress-bar компонент что и для `ImportJob`.

## DataFrame Pipeline

**Pipeline** — инструкция преобразования файла, хранящаяся в `Dataframe.instructions` как JSON `{reader, transforms[]}`. Состоит ровно из одного Reader и нуля или более Transform.

**Reader** — первая стадия pipeline: читает исходный файл (XLSX/CSV/XLS) и возвращает `pd.DataFrame`. Конфигурируется один раз на pipeline. Результат кэшируется в Redis в формате Apache Arrow/Feather; ключ кэша = `session_id + SHA1(reader_cfg)`.

**Transform** — одна атомарная операция над `pd.DataFrame` (select, rename, drop_na и т.д.), объявленная через декоратор `@transform`. Трансформы всегда создают копию DataFrame и не мутируют вход; это свойство используется при сборе ошибок.

**Session** — временный контекст загрузки файла (`dataframe/sessions.py`). Хранит исходный файл в `default_storage` (media/ или S3). Reader-кэш живёт отдельно в Redis и инвалидируется вместе с сессией.

**Preview** — HTTP-эндпоинт `POST /api/dataframe/preview/`. Принимает `session_id`, `instructions`, `up_to` (опционально), `offset`, `row_limit`. Возвращает **всегда HTTP 200**: при успехе — `{columns, rows, …, step_error: null}`; при ошибке шага — `{columns, rows, …, step_error: {step_index, message}}` с данными до ошибочного шага. Ошибка Reader-стадии — отдельный путь (HTTP 404/500).

**step_error** — описатель первого упавшего Transform в preview-ответе: `{step_index: int, message: str}`. `step_index` — 0-based индекс в массиве `transforms`. Когда шаг K падает, Pipeline останавливается; данные соответствуют состоянию после шага K−1. `step_error: null` означает успешное завершение всех шагов.

## SupplierFeed (Выгрузка)

**SupplierFeed** — периодический файл (или набор файлов/листов) от поставщика, содержащий **изменяемые** данные о товарах (цены, остатки, акции, склад и т.д.). Термин «выгрузка» принят со стороны поставщика: он *выгружает* файл, система его *принимает*. Не путать с «Импортом» (`ImportJob`) — тот обновляет постоянные характеристики товара. `SupplierFeed` — сессия, объединяющая все файлы одного периода от одного поставщика. Закрывается явно пользователем (кнопка «Обработать»), после чего запускается матчинг.

Жизненный цикл: `draft → processing → matched | partial | error`. Переход `partial → done` происходит автоматически, когда все записи MatchQueue разобраны (`SupplierFeedEntry.objects.filter(feed=…, product=None).count() == 0`).

**FeedMapping** — постоянная конфигурация на одного поставщика (`Supplier`). Описывает: какая колонка является `supplier_sku` (обязательный primary identity), какие колонки — дополнительные identity-поля (для эмбеддинга при матчинге), какие — переменные поля (цена, остаток и т.д.), а также `auto_match_threshold` (порог косинусного сходства для авто-матча, настраивается на поставщика). Создаётся один раз, переиспользуется для всех последующих `SupplierFeed` этого поставщика. Загрузка файлов — через существующий `dataframe/sessions.py`.

**Identity-поля** — поля строки выгрузки, маркированные пользователем в `FeedMapping` как идентификаторы товара у поставщика (например: артикул поставщика, название у поставщика). Используются для построения эмбеддинга строки выгрузки при первичном матчинге. Не путать с `supplier_sku` — тот является ключом `SupplierLink`, остальные identity-поля идут только в эмбеддинг.

**Переменные поля** — поля строки выгрузки, содержащие изменяемые данные (цена, остаток, склад, акции и т.д.). Сохраняются в `SupplierFeedEntry.data`.

**SupplierFeedEntry** — одна строка выгрузки в рамках сессии `SupplierFeed`. После матчинга содержит FK на `Product` (до матчинга — `NULL`). Хранит переменные поля в `data: JSONField` (схема определяется `FeedMapping` конкретного поставщика). Один `Product` может иметь `SupplierFeedEntry` от нескольких поставщиков — агрегация не нужна, текущее состояние = последняя запись по каждому поставщику.

**SupplierLink** — постоянная подтверждённая связь между строкой выгрузки конкретного поставщика и `Product`. Ключ: `(supplier, supplier_sku)` — уникальная пара `Supplier` + артикул поставщика. Создаётся при первом подтверждении матчинга (вручную или авто). В последующих выгрузках того же поставщика используется для мгновенного сопоставления без повторного эмбеддинга.

**MatchQueue** — очередь строк выгрузки, для которых автоматический матчинг не дал результата выше `FeedMapping.auto_match_threshold`. Не отдельная модель — это фильтр `SupplierFeedEntry.objects.filter(product=None)`. Кандидаты (Top-3..5 продуктов с косинусными скорами) хранятся в `SupplierFeedEntry.match_candidates: JSONField`. Пользователь разбирает очередь вручную — при подтверждении заполняется `product`, создаётся `SupplierLink`.

### Алгоритм матчинга (для каждой строки выгрузки)
1. Есть `SupplierLink(supplier, supplier_sku)`? → авто-матч, `SupplierFeedEntry.product` заполняется немедленно.
2. Нет → строится эмбеддинг из identity-полей строки → косинусное сравнение с `Product.embedding`.
3. Лучший скор ≥ `auto_match_threshold` → авто-матч + создать `SupplierLink`.
4. Скор < порога → `product = NULL`, топ-N кандидатов сохраняются в `match_candidates` → попадает в MatchQueue.

### Приложение
Весь функционал выгрузок живёт в новом Django-приложении **`supplier_feed`**. FKи: `product.Product`, `supplier_manager.Supplier`.

### Границы текущего скоупа
Интеграция `SupplierFeedEntry.data` с существующим `PriceManager` (пересчёт `MainProductPrice`) — **вне скоупа** текущей реализации.
