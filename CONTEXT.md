# Глоссарий предметной области — Price Manager

## Импорт (ImportJob)

**Импорт** — разовая операция загрузки файла поставщика для обновления **постоянных** характеристик товара (`Product.characteristics`, `sku`, `name`, `category` и т.д.). Выполняется через `ImportJob` (preview → commit). Не путать с Выгрузкой.

**rows_total** — общее число строк в DataFrame после применения pipeline. Устанавливается один раз, до начала записи в БД. Включает невалидные строки.

**rows_done** — число строк, *обработанных* воркером (валидных + пропущенных). Растёт после каждого батча. Не равно числу успешно записанных строк — итоговую разбивку (created / updated / skipped) см. в `ImportJob.result`.

**Прогресс-батч** — порция строк размером `IMPORT_COMMIT_BATCH_SIZE`, каждая в отдельной транзакции. После записи батча `rows_done` обновляется через `progress_callback`.

**Indeterminate-фаза** — стадии до начала записи в БД (`STAGE_OPENING_SESSION`, `STAGE_APPLYING_PIPELINE`, `STAGE_VALIDATING_ROWS`). В это время `rows_total == 0`; клиент показывает spinner. Отдельного флага `is_determinate` нет — `rows_total > 0` является достаточным условием для перехода на progress bar.

**Прогресс при ошибке** — если задача падает посередине коммита, `rows_done` не сбрасывается. Значение отражает реально обработанные строки (каждый батч — своя транзакция, откат не происходит). SPA показывает застывший bar с иконкой ошибки.

**Прогресс CharacteristicMutationJob** — `retype` и `rename` используют тот же паттерн: `rows_total` устанавливается через `COUNT` до начала итерации; `rows_done` — число пройденных продуктов (включая `skip_row` в rename). `rows_done` обновляется каждые `batch_size` итераций независимо от того, попал ли продукт в батч: скипнутые строки не пишутся в БД, но всё равно двигают счётчик. SPA может использовать тот же progress-bar компонент что и для `ImportJob`.

## DataFrame Pipeline

**Pipeline** — инструкция преобразования файла, хранящаяся в `Dataframe.instructions` как JSON `{reader, transforms[]}`. Состоит ровно из одного Reader и нуля или более Transform.

**Reader** — первая стадия pipeline: читает исходный файл (XLSX/CSV/XLS) и возвращает `pd.DataFrame`. Конфигурируется один раз на pipeline. Результат кэшируется в Redis в формате Apache Arrow/Feather; ключ кэша = `session_id + SHA1(reader_cfg)`.

**Transform** — одна атомарная операция над `pd.DataFrame` (select, rename, drop_na и т.д.), объявленная через декоратор `@transform`. Трансформы всегда создают копию DataFrame и не мутируют вход; это свойство используется при сборе ошибок.

**Session** — временный контекст загрузки файла (`dataframe/sessions.py`). Хранит исходный файл в `default_storage` (media/ или S3). Reader-кэш живёт отдельно в Redis и инвалидируется вместе с сессией.

**Preview** — HTTP-эндпоинт `POST /api/dataframe/preview/`. Принимает `session_id`, `instructions`, `up_to` (опционально), `offset`, `row_limit`. Возвращает **всегда HTTP 200**: при успехе — `{columns, rows, …, step_error: null}`; при ошибке шага — `{columns, rows, …, step_error: {step_index, message}}` с данными до ошибочного шага. Ошибка Reader-стадии — отдельный путь (HTTP 404/500).

**step_error** — описатель первого упавшего Transform в preview-ответе: `{step_index: int, message: str}`. `step_index` — 0-based индекс в массиве `transforms`. Когда шаг K падает, Pipeline останавливается; данные соответствуют состоянию после шага K−1. `step_error: null` означает успешное завершение всех шагов.

## SupplierFeed (Выгрузка)

**SupplierFeed** — периодический файл (или набор файлов/листов) от поставщика, содержащий **изменяемые** данные о товарах (цены, остатки, акции, склад и т.д.). Термин «выгрузка» принят со стороны поставщика: он *выгружает* файл, система его *принимает*. Не путать с «Импортом» (`ImportJob`) — тот обновляет постоянные характеристики товара. `SupplierFeed` — сессия, объединяющая все файлы одного периода от одного поставщика. Закрывается явно пользователем (кнопка «Обработать»), после чего запускается матчинг.

Жизненный цикл: `draft → processing → matched | partial | error`. Переход `partial → done` происходит автоматически, когда все записи MatchQueue разобраны (`SupplierFeedEntry.objects.filter(feed=…, product=None, skipped=False).count() == 0`).

**FeedMapping** — постоянная конфигурация на одного поставщика (`Supplier`). Содержит обязательную ссылку на **Pipeline** (`Dataframe` FK) — pipeline применяется к каждому загруженному файлу сессии и возвращает чистый `pd.DataFrame`. Описывает: какая колонка **выхода pipeline** является `supplier_sku` (обязательный primary identity), какие — дополнительные identity-поля (для эмбеддинга при матчинге), какие — переменные поля (цена, остаток и т.д.); а также `auto_match_threshold`. Дополнительно — опциональные маппинги для создания товара из выгрузки: `product_name_column` и `product_sku_column` (см. «Создание товара из выгрузки»). Создаётся один раз, переиспользуется для всех последующих `SupplierFeed` этого поставщика. Сырые файлы никогда не читаются напрямую — только через Pipeline.

**Identity-поля** — поля строки выгрузки, маркированные пользователем в `FeedMapping` как идентификаторы товара у поставщика (например: артикул поставщика, название у поставщика). Используются для построения эмбеддинга строки выгрузки при первичном матчинге. Не путать с `supplier_sku` — тот является ключом `SupplierLink`, остальные identity-поля идут только в эмбеддинг.

**Переменные поля** — поля строки выгрузки, содержащие изменяемые данные (цена, остаток, склад, акции и т.д.). Сохраняются в `SupplierFeedEntry.data`.

**SupplierFeedEntry** — одна строка выгрузки в рамках сессии `SupplierFeed`. После матчинга содержит FK на `Product` (до матчинга — `NULL`). Хранит объединение identity-полей и переменных полей в `data: JSONField` (при пересечении переменные поля перезаписывают identity-поля, но значения из одной строки, так что расхождений нет). Один `Product` может иметь `SupplierFeedEntry` от нескольких поставщиков — агрегация не нужна, текущее состояние = последняя запись по каждому поставщику.

**SupplierLink** — постоянная связь между артикулом поставщика и `Product`. Ключ: `(supplier, supplier_sku)` — уникальная пара `Supplier` + артикул поставщика. Поле `product` — nullable FK: если `product` заполнен, это подтверждённый матч; если `product = NULL` — это **игнор-линк**. Создаётся при первом подтверждении матчинга (вручную или авто). В последующих выгрузках того же поставщика используется для мгновенного сопоставления без повторного эмбеддинга.

**Игнор-линк** — `SupplierLink` с `product = NULL`. Означает постоянный игнор артикула поставщика: при следующей выгрузке матчинг видит игнор-линк и немедленно помечает строку как `skipped=True`, не кладя её в MatchQueue и не тратя ресурсы на эмбеддинг. Создаётся действием «Игнорировать» в MatchQueue. Может быть переназначен на реальный товар через PATCH `/api/supplier-feed/links/{id}/`.

**MatchQueue** — очередь строк выгрузки, для которых автоматический матчинг не дал результата выше `FeedMapping.auto_match_threshold`. Не отдельная модель — это фильтр `SupplierFeedEntry.objects.filter(product=None, skipped=False)`. Кандидаты (Top-N продуктов с косинусными скорами) хранятся в `SupplierFeedEntry.match_candidates: JSONField` в формате `{product_id, score, name, sku, category, brand}` — денормализованы в момент матчинга. Лучший скор дополнительно денормализован в `SupplierFeedEntry.best_score: FloatField(null=True)` для эффективной сортировки. Очередь отображается в порядке `ORDER BY best_score DESC NULLS FIRST`: записи без кандидатов (аномалия — эмбеддер мог быть недоступен) идут первыми, затем записи с высоким скором (близко к порогу — ручной матч), затем записи с низким скором (вероятно новые товары). Пользователь разбирает очередь вручную через пять действий:

| Действие | Результат |
|---|---|
| Привязать к существующему товару | `entry.product` заполняется, создаётся `SupplierLink` |
| Создать новый товар (единично) | Создаётся `Product(draft)` + `SupplierLink`, `entry.product` заполняется |
| Создать новые товары (bulk) | Для всех оставшихся записей в очереди атомарно создаются `Product(draft)` + `SupplierLink` |
| Пропустить (для этой сессии) | `entry.skipped = True` |
| Игнорировать (навсегда) | Создаётся игнор-линк, `entry.skipped = True` |

**Создание товара из выгрузки** — действие в MatchQueue, создающее `Product` со статусом `draft` непосредственно из строки выгрузки. Атомарно: в одной транзакции создаётся `Product` (поля `sku` и `name`), `SupplierLink` и заполняется `SupplierFeedEntry.product`. Форма подтверждения предзаполняется из строки выгрузки согласно опциональным маппингам `FeedMapping.product_name_column` и `FeedMapping.product_sku_column`; если маппинги не заданы, поля заполняются вручную. Категория, бренд и характеристики доставляются позже через обычный редактор `Product`.

**Bulk-создание товаров из выгрузки** — действие уровня очереди (не отдельной записи). Создаёт `Product(draft)` + `SupplierLink` для всех оставшихся записей очереди (`product=None, skipped=False`) одним запросом. Перед запуском пользователь подтверждает колонку `name` в диалоге — диалог всегда показывается, предзаполнен значением `FeedMapping.product_name_column` (если задано), но может быть изменён. SKU берётся из `FeedMapping.product_sku_column` если задано, иначе из `entry.supplier_sku`. Поведение при ошибках — skip-and-continue: записи с конфликтом SKU или отсутствующей колонкой `name` пропускаются и остаются в очереди; ответ возвращает `{created, failed, errors: [{entry_id, reason}]}`. Типичный сценарий: пользователь сначала вручную разбирает записи с высоким скором (вероятные совпадения), а затем запускает bulk-создание для хвоста очереди с низкими скорами.

### Алгоритм матчинга (для каждой строки выгрузки)
1. Есть `SupplierLink(supplier, supplier_sku)` с `product = NULL` (игнор-линк)? → `entry.skipped = True`, строка не попадает в MatchQueue.
2. Есть `SupplierLink(supplier, supplier_sku)` с `product` заполненным? → авто-матч, `SupplierFeedEntry.product` заполняется немедленно.
3. Нет → строится эмбеддинг из identity-полей строки → косинусное сравнение с `Product.embedding`.
4. Лучший скор ≥ `auto_match_threshold` → авто-матч + создать `SupplierLink`.
5. Скор < порога → `product = NULL`, топ-N кандидатов сохраняются в `match_candidates`, лучший скор — в `best_score` → попадает в MatchQueue.
6. Нет товаров с эмбеддингами в БД → `match_candidates = []`, `best_score = NULL` → попадает в MatchQueue (отображается первым как аномалия).

### Приложение
Весь функционал выгрузок живёт в новом Django-приложении **`supplier_feed`**. FKи: `product.Product`, `supplier_manager.Supplier`.

### Границы текущего скоупа
Интеграция `SupplierFeedEntry.data` с существующим `PriceManager` (пересчёт `MainProductPrice`) — **вне скоупа** текущей реализации.
